## AC-2: the core loop stalls on name resolution during the block

Both runs, probe trace (`ac2-*/stderr.txt`): 5 × `Dns Ok` (3 s apart, before the block), then `Dns Timeout 2001 ms`,
then one HTTP probe that fails (`Timeout 1500 ms` for drop, `Refused 0 ms` for return: the pf rule was active),
then 6 × `Http Ok` 1 s apart and one `Dns Ok`. 14 probes over ~67 s of app life; at the configured intervals
(3 s healthy, 1 s suspect) it would be at least ~22. The missing ~35 s sit exactly in the rest of the block.

Cause in code: `run.rs` `probe()` calls `prober.resolve_http()` (std `to_socket_addrs`, a blocking `getaddrinfo` with no
timeout) on the core thread before every HTTP probe while health is `Healthy`/`Unknown`. One DNS timeout does not leave
`Healthy`, so the next HTTP probe re-resolves `captive.apple.com`; with all egress blocked the system resolver hangs
until the block ends, then the probes pass and nothing was ever lost. T-13's 25 s block on "lutix" passed, probably
because there the resolve returned quickly (cached). Not proven by timestamps: trace lines carry none.

Proposed new task (not fixed here): **HTTP target resolution must never block the core loop** — resolve on a worker thread
with a deadline ≤ `http_timeout`, keep the last address on timeout/failure (and treat a resolve timeout as a probe
failure); add a timestamp to every trace line. DoD: a run.rs test with a `Prober` whose `resolve_http` blocks 60 s →
`connectivity_lost` ≤ 10 s; live `tools/live/ac2.sh drop` and `ac2.sh return` PASS.
