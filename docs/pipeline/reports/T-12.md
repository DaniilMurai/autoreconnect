## Findings
- Power on after `wifi_off_by_user` logs no `wifi_on_by_user`: the first link after power-on is `Disassociated`, and
  `Policy` goes WifiOffByUser → NotAssociated with `connectivity_lost {to: not_associated}` (policy.rs, `PoweredOff`/`Disassociated` arms).
- Right after the OS rejoins, DNS probes return `Refused` for ~3 s (no route yet); `Policy` counted them →
  `connection_degraded` + `power_cycle` 7 s after the user's power-on (dry run, so nothing happened). Same after a disconnect: NoInternet → `power_cycle` 30 s in.
- CoreWLAN sends bursts (4–6 callbacks per toggle); `run` drains the channel and reads the link once per burst.
- The delegate is called on CoreWLAN's own queue: the core thread needed no run loop.

## Proposed changes to tasks.md / contracts.md
- New policy task: on PoweredOff/WifiOffByUser → Disassociated, log `wifi_on_by_user` and treat it as NotAssociated
  without `connectivity_lost`; after a fresh association, don't count `Refused`/`NotReady` probes for a short settle
  (like `settle_after_power_cycle`). Without it, AC-5 and AC-4a runs log false losses and actions.
