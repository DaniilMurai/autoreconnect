## What changed
- `run.rs`: `HttpResolver` runs `resolve_http` on a worker; the core waits ≤ `http_timeout`; a timeout = an HTTP `Timeout` probe; the last good address is kept; the startup resolve no longer blocks before `app_started`. Trace lines start with local `HH:MM:SS.mmm`.
- `probe.rs`: the DNS probe keeps its own deadline (each stray datagram used to restart the socket timeout). Other core-thread calls checked: HTTP and gateway probes already had deadlines; `scutil`/`route -n` are local; join, keychain import and power-cycle block by design.
- `recovery_action.ts` = the action's start (user decision 2026-11-06); `check_log.py ac4b` adds `duration_ms`.
## Findings
- A reassociate under the block can fail in 83 ms with `NotInRange` (fresh scan on a weak signal); the power-cycle then recovers.
- With a 40 s block the power-cycle lands within ±1 s of the unblock; restore then depends on the OS reassociating (5.6 s and 13.8 s seen). AC-2 return may be flaky on weak networks.
- The first launch after each rebuild waits ~30 s on the Location prompt (new ad-hoc signature); `ac2.sh`'s 12 s lead-in would then start the block before `app_started`.
